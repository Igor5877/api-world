# Документація API (SkyBlock LXD Manager)

Цей документ містить детальний опис структури, файлів, класів та методів API-бекенду системи керування островами SkyBlock.

## 1. Основні файли

### `app/main.py`
Головний файл входу в додаток FastAPI.

*   **Функції:**
    *   `reconcile_island_states()`:
        *   **Параметри:** Немає.
        *   **Результат:** `None`.
        *   **Логіка:** Виконується при запуску API. Отримує список островів з БД, які знаходяться в активних або перехідних станах (RUNNING, PENDING_START тощо), і порівнює їх з реальним станом контейнерів у LXD. Якщо є розбіжності (наприклад, контейнер зупинено в LXD, але він RUNNING у БД), оновлює стан у БД.
    *   `lifespan(app: FastAPI)`:
        *   **Параметри:** `app` (екземпляр FastAPI).
        *   **Результат:** Асинхронний контекст-менеджер.
        *   **Логіка:** Керує циклом життя додатка. При старті: ініціалізує Redis, запускає прослуховувач Redis-повідомлень, виконує синхронізацію станів (через лідера) та запускає воркери черг. При зупинці: закриває з'єднання з Redis.
    *   `websocket_endpoint(websocket: WebSocket, client_id: str)`:
        *   **Параметри:** `websocket`, `client_id` (UUID гравця).
        *   **Результат:** `None`.
        *   **Логіка:** Обробляє WebSocket-з'єднання від плагіна Velocity або клієнтів. Додає з'єднання в менеджер і чекає на повідомлення (використовується переважно для сповіщень про зміну статусу острова).
        *   **Важливо:** Цей ендпоінт НЕ використовує префікс `/api/v1`. Пряма адреса: `/ws/{client_id}`.

## 2. Ядро (`app/core/`)

### `app/core/config.py`
Клас `Settings` для керування налаштуваннями через змінні середовища (.env).
*   **Параметри:** `DATABASE_URL`, `LXD_SOCKET_PATH`, `REDIS_URL`, ліміти серверів, таймери заморозки тощо.

### `app/core/redis.py`
Керування підключенням до Redis.
*   `init_redis_pool()`: Створює пул з'єднань з Redis, перевіряє доступність через `ping`.
*   `close_redis_pool()`: Закриває з'єднання.
*   `get_redis_client()`: Повертає активний клієнт Redis.

---

## 3. База даних (`app/db/`)

### `app/db/session.py`
Налаштування SQLAlchemy для асинхронної роботи з БД.
*   `get_db_session()`: Dependency для FastAPI. Створює асинхронну сесію, фіксує (commit) зміни при успіху або відкочує (rollback) при помилці.
*   `init_db()`: Створює таблиці в БД на основі моделей SQLAlchemy (використовується переважно при розробці).

---

## 4. Моделі та Схеми (`app/models/`, `app/schemas/`)

### `app/models/island.py`
*   `Island`: Основна модель острова. Містить `team_id`, `container_name`, `status`, `internal_ip_address`, `minecraft_ready` (прапор готовності сервера всередині контейнера).
*   `IslandQueue`: Черга на створення островів.
*   `IslandSetting`: Налаштування конкретного острова.
*   `IslandBackup`: Дані про бекапи (снапшоти) островів.

### `app/models/team.py`
*   `Team`: Модель команди. Кожен острів тепер належить команді. Містить `name` та `owner_uuid`.
*   `TeamMember`: Зв'язок гравців з командами (ролі: owner, moderator, member).

---

## 5. CRUD операції (`app/crud/`)

### `app/crud/crud_island.py`
Клас `CRUDisland` для прямої роботи з таблицею островів.
*   `get(db, island_id)`: Пошук за ID.
*   `get_by_team_id(db, team_id)`: Пошук острова команди.
*   `create(...)`: Додає новий запис про острів у БД.
*   `update(...)`: Оновлює поля острова (наприклад, IP або статус).
*   `update_status(...)`: Атомарне оновлення статусу.

### `app/crud/crud_team.py`
Методи для роботи з командами.
*   `get_team_by_player(db, player_uuid)`: Знаходить команду, в якій перебуває гравець.
*   `create_team(...)`: Створює команду та додає власника як першого члена.
*   `add_member(...)`, `remove_member(...)`: Керування складом команди.

## 6. Сервіси та Бізнес-логіка (`app/services/`)

### `app/services/lxd_service.py`
Взаємодія з LXD API через бібліотеку `pylxd`. Всі методи виконуються в окремих потоках (`run_in_executor`), щоб не блокувати асинхронний цикл.
*   `clone_container(...)`: Створює новий контейнер з базового образу.
*   `start_container(...)`, `stop_container(...)`, `freeze_container(...)`, `unfreeze_container(...)`: Керування станом контейнера.
*   `get_container_ip(...)`: Спроби отримати IP-адресу контейнера (з повторами, доки LXD не призначить IP).
*   `push_file_to_container(...)`: Запис файлів всередину контейнера (використовується для конфігурації `skyblock_island_data.toml`).

### `app/services/island_service.py`
Головний сервіс, що поєднує БД та LXD. Містить основну бізнес-логіку.

*   `start_island_instance(db_session, player_uuid, player_name, background_tasks)`:
    *   **Вхідні дані:** Сесія БД, UUID гравця, ім'я гравця, об'єкт фонових завдань.
    *   **Результат:** `IslandResponse` (об'єкт з даними про острів).
    *   **Детальна логіка:**
        1. Шукає команду гравця за його `player_uuid`.
        2. **Якщо команду знайдено:**
            *   Перевіряє наявність острова у цієї команди.
            *   Якщо острів є: викликає внутрішній метод `_start_existing_island`.
            *   Якщо острова немає: генерує назву контейнера, створює запис острова в БД зі статусом `PENDING_CREATION` і додає фонову задачу `_perform_lxd_clone_and_update_status`.
        3. **Якщо команду НЕ знайдено:**
            *   Шукає застарілий (legacy) соло-острів гравця.
            *   Якщо знайдено: викликає `_start_existing_island`.
            *   Якщо нічого не знайдено: викликає `create_new_solo_island` (створює команду і острів).
    *   **Перевірки:** Перевіряє, чи не перебуває острів уже в стані запуску, щоб не дублювати запити.

*   `_start_existing_island(db_session, island, team, background_tasks)`:
    *   **Вхідні дані:** Сесія БД, модель острова, модель команди, фонові завдання.
    *   **Логіка:**
        1. Якщо статус `RUNNING` — просто оновлює `last_seen_at` і надсилає сповіщення.
        2. Якщо статус `STOPPED`, `FROZEN` або `ERROR_START`:
            *   Змінює статус у БД на `PENDING_START`.
            *   Додає фонову задачу на фізичний запуск контейнера (`_perform_lxd_start_and_update_status`).
        3. Повертає актуальні дані острова.

*   `_perform_lxd_start_and_update_status(team_id, container_name, was_frozen)`:
    *   **Логіка (фонова):**
        1. Відкриває нову сесію БД.
        2. Якщо `was_frozen` — викликає `unfreeze_container` у LXD.
        3. Якщо контейнер не запущений — викликає `start_container`.
        4. Циклічно (до 10 разів) намагається отримати IP-адресу контейнера.
        5. Оновлює в БД: `status = RUNNING`, `internal_ip_address = IP`, `minecraft_ready = False`.
        6. Надсилає WebSocket-сповіщення всім членам команди про те, що сервер запускається.

*   `mark_island_as_ready_for_players(db_session, owner_uuid)`:
    *   **Логіка:**
        1. Знаходить команду за UUID власника.
        2. Перевіряє, чи острів у стані `RUNNING`.
        3. Встановлює `minecraft_ready = True` у БД.
        4. Розсилає WebSocket-сповіщення. Тепер Velocity знатиме, що гравця можна перенаправляти.

*   `handle_join_team(db_session, player_to_join_uuid, team_to_join, background_tasks)`:
    *   **Логіка:**
        1. Перевіряє, чи не є гравець вже членом цієї команди.
        2. Перевіряє поточну команду гравця.
        3. Якщо гравець у соло-команді (тільки він один):
            *   Видаляє стару соло-команду.
            *   Додає фонову задачу на видалення старого LXD-контейнера.
        4. Додає гравця в нову команду `team_to_join`.

### `app/services/websocket_manager.py`
Менеджер WebSocket-з'єднань.
*   Використовує Redis Pub/Sub для синхронізації між декількома воркерами API. Повідомлення про зміну статусу острова публікується в Redis, а всі воркери перевіряють, чи підключені до них відповідні гравці, і відправляють їм дані.
*   **Усунення несправностей:** Якщо WebSocket не підключається або повідомлення не доходять:
    1. Перевірте, чи запущений **Redis** (без нього WebSocket у цьому проєкті не працюватиме).
    2. Перевірте логі API на наявність помилок "ConnectionRefusedError" до Redis.
    3. Переконайтеся, що ви підключаєтесь до кореня API (`/ws/...`), а не через `/api/v1/ws/...`.
    4. **Якщо отримуєте 404**:
        *   **Важливо**: `curl` завжди повертатиме 404 на WebSocket-ендпоінт. Це нормально. Використовуйте `wscat` для тестів.
        *   Переконайтеся, що API не запущено з параметром `--root-path`. Якщо цей параметр встановлено (наприклад, у `/api/v1`), то WebSocket також "переїде" за нову адресу.
        *   Перевірте встановлені пакети: `pip install websockets`.

## 7. Ендпоінти (`app/api/v1/endpoints/`)

### `islands.py`
*   `GET /{player_uuid}`: Отримати поточний статус острова.
*   `POST /start/{player_uuid}`: Запит на запуск острова.
*   `POST /stop/{player_uuid}`: Запит на зупинку.
*   `POST /{owner_uuid}/ready`: Сигнал від мода про готовність.

### `teams.py`
*   `POST /create_solo`: Створення команди для соло-гри.
*   `GET /my_team/{player_uuid}`: Інформація про команду гравця.
*   `POST /accept_invite`: Прийняття запрошення в команду.
