# Звіт про аналіз проекту SkyBlock System

Цей документ містить детальний аналіз кодової бази системи SkyBlock, включаючи API (FastAPI), плагін Velocity (Java) та мод сервера Forge (Java). Аналіз зосереджений на виявленні критичних помилок, проблем з продуктивністю, безпекою та логікою роботи.

## 1. Загальний огляд

Система має сучасну мікросервісну архітектуру, що складається з центрального API для управління контейнерами LXD, проксі-сервера Velocity для маршрутизації гравців та серверного моду Forge для ігрової логіки. Код загалом добре структурований, використовує асинхронність (Python `asyncio`, Java `CompletableFuture`), але містить кілька критичних недоліків, які можуть призвести до нестабільності в продакшн-середовищі.

## 2. Критичні помилки (Critical Errors)

Ці проблеми вимагають негайного виправлення, оскільки вони можуть спричинити падіння серверів, зависання або втрату даних.

### 2.1. Блокування основного потоку сервера (Forge Mod)
*   **Файл:** `mods-server/src/main/java/com/skyblock/dynamic/nestworld/mods/NestworldModsServer.java`
*   **Метод:** `refreshAndGetTeamId`
*   **Опис:** Метод використовує синхронний виклик `httpClient.send(...)`. Якщо цей метод викликається з основного потоку сервера Minecraft (Main Thread) — наприклад, під час входу гравця або завантаження квестів — і API відповідає повільно або недоступне, **весь сервер "зависне"** на час тайм-ауту (до 10 секунд).
*   **Наслідки:** "Lag spikes", тайм-аути гравців, спрацювання Watchdog і краш сервера.
*   **Рішення:** Переписати на асинхронний виклик (`sendAsync`) і обробляти результат через `CompletableFuture` або використовувати окремий потік для запитів.

### 2.2. Race Conditions при старті API
*   **Файл:** `api/app/main.py` (функція `reconcile_island_states`)
*   **Опис:** При старті воркера відбувається звірка станів (Reconciliation). Хоча використовується Redis-лок (`startup_lock`), логіка не враховує ситуацію, коли запити від гравців починають надходити до завершення цього процесу.
*   **Наслідки:** Можливий конфлікт, коли API одночасно намагається "полагодити" статус острова (наприклад, перевести з `RUNNING` в `STOPPED`, бо контейнер впав) і обробити запит гравця на вхід, що призведе до некоректного стану в БД.

### 2.3. Відсутність автентифікації на критичних ендпоінтах
*   **Компонент:** API (`api/app/api/v1/endpoints/`)
*   **Опис:** Ендпоінти, такі як `/islands/{uuid}/ready` або `/islands/stop/{uuid}`, схоже, не мають перевірки токена або API-ключа.
*   **Наслідки:** Зловмисник, знаючи UUID гравця, може відправляти фейкові запити на зупинку або запуск серверів, або підробляти статус "готовності".
*   **Рішення:** Впровадити перевірку `X-API-Key` або JWT токенів для міжсервісної взаємодії.

## 3. Важливі попередження (Major Warnings)

### 3.1. Управління з'єднаннями WebSocket (Velocity)
*   **Файл:** `Nestworldvelocity/src/main/java/com/skyblockdynamic/nestworld/velocity/network/WebSocketManager.java`
*   **Опис:** Використовується `CountDownLatch`, що блокує потік. Хоча `connect()` асинхронний, логіка закриття та обробки помилок повинна гарантувати, що з'єднання не "висять" вічно. Також, при частому перепідключенні гравця можуть створюватися дублікати з'єднань, якщо старі не встигли закритися.
*   **Рішення:** Додати більш жорсткий контроль життєвого циклу WebSocket-клієнта.

### 3.2. Жорстка залежність від FTB Quests
*   **Файл:** `mods-server/build.gradle` та код
*   **Опис:** Мод має пряму залежність від `ftb-quests`. Якщо FTB Quests змінить API або буде видалений, серверний мод перестане працювати.
*   **Рішення:** Використовувати абстракцію або "м'яку" залежність (soft dependency), перевіряючи наявність моду в рантаймі.

### 3.3. Обробка помилок API у Velocity
*   **Файл:** `Nestworldvelocity/.../commands/MyIslandCommand.java`
*   **Опис:** Якщо API повертає помилку 500 або 502 (Bad Gateway), плагін просто пише повідомлення гравцю. Немає механізму "retry" з експоненціальною затримкою або fallback-логіки для критичних ситуацій.

### 3.4. Валідація IP-адрес
*   **Файл:** `api/app/schemas/island.py`
*   **Опис:** Використовується простий Regex для IP (`^\d{1,3}\.\d{1,3}...`). Це пропускає некоректні IP (наприклад, `999.999.999.999`).
*   **Рішення:** Використовувати бібліотеку `ipaddress` для валідації.

## 4. Рекомендації щодо покращення (Recommendations)

1.  **Логування та моніторинг:** Додати Prometheus-метрики для відстеження кількості активних островів, часу відповіді API та кількості помилок.
2.  **LXD Клієнт:** Переконатися, що клієнт LXD в API використовує пул з'єднань або коректно закриває сесії, щоб уникнути вичерпання файлових дескрипторів при високому навантаженні.
3.  **Конфігурація:** Винести всі хардкод-значення (таймаути, ліміти спроб) у конфігураційні файли або змінні середовища.
4.  **Безпека:**
    *   Закрити API від зовнішнього світу (firewall), дозволивши доступ тільки з IP проксі та ігрових серверів.
    *   Додати перевірку цілісності даних (HMAC) для повідомлень між серверами.

## 5. Детальний аналіз по компонентах

### API (FastAPI)
*   **Плюс:** Використання `sqlalchemy[asyncio]` — це добре для продуктивності.
*   **Мінус:** В `crud_island.py` та інших CRUD модулях, методи `create` додають об'єкт в сесію, але не роблять `flush/commit`. Це перекладає відповідальність на сервіс, що може призвести до помилок, якщо сервіс "забуде" зробити коміт. Рекомендується явно керувати транзакціями або використовувати патерн "Unit of Work".
*   **Мінус:** `IslandService.create_new_solo_island` виконує багато дій (БД, LXD) в одному потоці виконання (хоч і асинхронно). Якщо LXD відповідає довго, це затримує відповідь API. Варто винести важкі операції LXD повністю у Background Tasks (що частково зроблено, але створення запису в БД має бути атомарним).

### Velocity Plugin
*   **Плюс:** Добре використання `CompletableFuture` для асинхронності.
*   **Мінус:** Локалізація (`LocaleManager`) завантажує файли при старті. Якщо файл зміниться, треба перезавантажувати плагін. Варто додати команду перезавантаження конфігу.
*   **Мінус:** `TpaCommand` зберігає запити в `ConcurrentHashMap` в пам'яті. При перезавантаженні проксі всі запити втрачаються. Це не критично, але варто врахувати.

### Forge Mod
*   **Плюс:** Використання подій Forge (`ServerStartedEvent`, `PlayerLoggedInEvent`) реалізовано коректно.
*   **Мінус:** `Config.validateUrl` використовує дуже спрощений Regex. Краще використовувати `java.net.URL` для валідації.
*   **Мінус:** Відсутність кешування `TeamData` на стороні клієнта (якщо це потрібно для GUI) може створювати зайвий трафік.
