## Ліцензійне питання FTB Quests

**Висновок: вендорена та модифікована копія FTB Quests у публічному репозиторії з високою ймовірністю порушує ліцензію. (Це не юридична консультація.)**

Версія FTB Quests 1.20.1 у каталозі `FTB-Quests-1.20.1-main/` сама декларує свої умови:
- `forge/src/main/resources/META-INF/mods.toml` → `license = "All Rights Reserved"`
- `fabric/src/main/resources/fabric.mod.json` → `"license": "All Rights Reserved"`
- `README.md` копії: *"All Rights Reserved to Feed The Beast Ltd. Source code is `visible source`"* — код відкритий лише для перегляду та для PR-ів у їхній репозиторій (з підписаним CLA). Права на модифікацію та розповсюдження похідних версій ліцензія не надає.

Чому це проблема саме тут (репозиторій `Igor5877/api-world` — **публічний**):
1. Публічно розповсюджується **модифікований вихідний код** FTB Quests (увесь `FTB-Quests-1.20.1-main/` з правками) — похідна робота без дозволу правовласника.
2. Публічно розповсюджується **скомпільований jar**: `mods-server/libs/ftb-quests-2001.4.14-transformProductionForge.jar`.
3. **Відсутній файл `LICENSE.md`** у вендореній копії, хоча README на нього посилається — видалення копірайт-нотисів погіршує ситуацію.
4. Запуск модифікованої збірки на власному сервері — найменш ризикована частина, але формально ARR не дозволяє і модифікацію.

### Що зроблено у твоїй копії FTB Quests
Захист від повторного фарму квестів між серверами реалізовано через:
- Перейменування `TeamData` → `IslandData` (`IslandData.java`), ключ = UUID власника острова.
- Guard у двох C2S-пакетах — прогрес/нагороди зараховуються лише на власному острові команди:
  - `net/SubmitTaskMessage.java:51-55`
  - `net/ClaimRewardMessage.java:57-61`
- Авторитетна перевірка членства через `QuestTeamBridge.isPlayerOnTeam()` (дані з API).

### Рекомендації (від простого до правильного)
1. **Негайно:** зробити репозиторій приватним АБО прибрати `FTB-Quests-1.20.1-main/` і jar з репо (і з git-історії через `git filter-repo`).
2. **Написати FTB** і попросити дозвіл — вони часто дають його на запит для приватних некомерційних серверів.
3. **Найчистіший технічний шлях:** прибрати форк, а точкові правки (guard у двох пакетах + резолвінг team id) перенести у власні **Mixin-и** в `mods-server`, використовуючи оригінальний FTB Quests jar як звичайну залежність. Тоді редистрибуції чужого коду немає.
4. **Альтернатива:** мігрувати на квест-мод з відкритою ліцензією (напр. Heracles, MIT).

### Зауваження до самого захисту (баги логіки)
- **Дірка на не-острівних серверах:** guard містить `!SkyBlockMod.isIslandServer()`, тож на хабі/будь-якому не-острівному сервері захист повністю вимкнений — якщо там завантажені квести, повторний фарм повертається. Зробити guard явним: на не-острівному сервері завжди `false`.
- **NPE:** `UUID.fromString(SkyBlockMod.getOwnerUuid())` впаде, якщо `isIslandServer()==true`, але `getOwnerUuid()==null`. Спершу перевіряти на null.
- **Stale-кеш:** при недоступності API `loadTeamDataFromCache()` дозволяє щойно виключеному учаснику фармити прогрес команди.

## Критичні проблеми

### API-бекенд (`/api/`)
1. **Гонка станів машини станів острова** — `services/island_service.py:282-290, 425-430`. Переходи статусів не захищені `SELECT ... FOR UPDATE` чи optimistic locking; паралельні start/freeze можуть розійтися зі станом контейнера.
2. **Подвійні комміти / неконсистентні транзакції** — `db/session.py:76-79` авто-коммітить, але CRUD і сервіси теж коммітять самі (`island_service.py:231, 252, 285`). Фонові задачі відкривають власні сесії через `AsyncSessionLocal()` без узгодження — ризик `DetachedInstanceError` і втрачених оновлень.
3. **Перехоплення WebSocket `client_id`** — `main.py:269-336` + `services/websocket_manager.py:20-41`. `client_id` береться з URL без перевірки; з валідним ключем можна підключитись як `island_<uuid_жертви>` і отримувати чужі повідомлення. Якщо ключі не налаштовані — автентифікації немає взагалі. (C-2 у SECURITY_AUDIT.md.)

### Forge-мод (`/mods-server/`)
4. **Блокуючий HTTP у потоці сервера** — `NestworldModsServer.java:136`. Синхронний `httpClient.send()` викликається з `getCachedTeamId()` під час обробки submit/claim; при таймауті API тік острівного сервера зависає до 10 с.

## Серйозні проблеми

### Бекенд
- **Слабка leader-election при старті** (`main.py:231`) — `SET NX` з TTL 60с; довга реконсиляція дозволяє другому воркеру запустити її повторно.
- **Реконсиляція станів** (`main.py:86-186`) — може перезаписати конкурентні оновлення; O(N) послідовних викликів до LXD без паралелізації.
- **LXD-операції без зовнішнього таймауту** (`lxd_service.py:80, 131-150`) — зависання демона блокує потоки executor'а.
- **Ринок:** `record_sell_transaction` (`crud_market.py`) пише без блокування рядка товару (на відміну від `purchase_item` з `with_for_update()`).
- **Rate limiting лише на `/inventory/sync`** — start/purchase/teams не обмежені.

### Velocity-плагін (`/Nestworldvelocity/`)
- **Нескінченний полінг** (`PlayerConnectionListener.java:126-180`) — будь-яка не-200 відповідь вважається тимчасовою; перманентний ERROR-стан політься вічно.
- **JSON без null-чеків** (там само, 136-143) — `islandData.get("status").getAsString()` кидає NPE при неповній відповіді.
- **Витік ресурсів** — `Map<UUID, WebSocketManager>` (`NestworldVelocityPlugin.java:54`) не чиститься; `newCachedThreadPool()` необмежений.
- **URL-injection через playerName** (C-4) — ім'я не URL-кодується перед підстановкою в запит.

### Мод (`/mods-server/`)
- **Гонка на `freezeTask`** (`PlayerEventHandler.java:42-45`) — не-volatile поле без синхронізації.

### RealMarket (`/RealMarket/`)
- WebSocket-реконнект кожні 30с **без backoff** (`MarketSyncManager.java:591-596`).
- Невдалі sync-запити **не ретраяться** — дані губляться (`MarketSyncManager.java:259-268`).
- Гонка на `ae2Ready` — можлива подвійна екстракція з черги.
- Клієнт контролює amount/UUID (`PacketShopAction`); можливе цілочисельне переповнення (`PacketTrade.java`) — C-6, H-4.

## Інфраструктура та інше
- **CI/CD:** загалом добре (секрети в GitHub Secrets, бекап + авто-rollback), але `_deploy-api-ssh.yml:69` і `_deploy-lxc-jar.yml:86` ставлять `StrictHostKeyChecking no` — ризик MITM.
- **UUID-енумерація:** `GET /warps/player-uuid/{player_name}` (`warps.py:75-87`) дозволяє зібрати UUID усіх гравців (H-2).
- **API-ключі без розмежування прав** — один ключ дає доступ і до проксі-операцій, і до адмінських; будь-який власник ключа може видалити чужий warp.
- **Схема БД:** market-таблиці посилаються на `island_uuid` як VARCHAR без FK до `islands`/`teams` (міграція на `team_id` у `schema.sql:181-209` не завершена).
- **Гігієна репо:** закоммічений `mods-server/libs/ftb-quests-...jar` (1.2 МБ) винести в залежності; `/test/` — покинута заглушка.
- **Тести** покривають лише happy-path з моками; немає тестів на конкурентність, відкати транзакцій, падіння фонових задач.

### Не виправлено в цьому проході (потребують більших/архітектурних змін)
- Гонки станів машини острова (`SELECT ... FOR UPDATE` / optimistic locking).
- Узгодження транзакцій: прибрати дублюючі комміти в CRUD/сервісах.
- Quorum-lock для leader-election при старті.
- LXD-операції із зовнішнім таймаутом; паралелізація реконсиляції.
- Ринок: блокування рядка в `record_sell_transaction`; rate limiting на всіх ендпоінтах.
- RealMarket: backoff на реконнект, retry для sync, гонка `ae2Ready`.
- FK-constraint'и для market-таблиць; розмежування API-ключів за скоупами; UUID-енумерація (H-2).
- **Ліцензія FTB Quests:** прибрати вендорений форк з публічного репо й перенести правки в Mixin-и (див. розділ вище) — головний пункт, який варто закрити окремо.
