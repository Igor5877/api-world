# Детальний аудит кодової бази SkyBlock Dynamic

Цей звіт містить аналіз чотирьох основних модулів системи: бекенд API (`api/`), плагін для Velocity (`Nestworldvelocity/`), серверний мод острова (`mods-server/`), мод економіки та синхронізації `RealMarket/` та інтегрований модуль квестів `FTB-Quests-1.20.1-main/`. Оцінка проводилася за критеріями: ефективність, безпека, архітектура та інструменти адміністрування.

---

## 1. Модуль: `api/` (FastAPI Бекенд)

### Безпека
*   **Проблема (CORS):** У `main.py` налаштовано `CORSMiddleware` з `allow_origins=["*"]` та `allow_credentials=True`. Це створює критичну вразливість, оскільки дозволяє будь-якому веб-сайту робити запити від імені автентифікованого користувача (SSRF/Data leakage).
*   **Як має бути:** Замість `["*"]` слід використовувати список дозволених доменів (наприклад, читати їх з `settings.CORS_ORIGINS`).
*   **Проблема (Автентифікація та авторизація API):** Багато ендпоінтів (наприклад, зупинка/замороження островів, зміна назви команди, адміністративні операції) приймають UUID або інші параметри напряму, без належної перевірки прав доступу (відсутні механізми перевірки JWT або API токенів). Будь-хто, хто знає або підбере UUID гравця, може маніпулювати його островом.
*   **Як має бути:** Кожен захищений ендпоінт повинен використовувати систему залежностей (Depends) у FastAPI для перевірки авторизаційного токена гравця чи адміністратора.

### Архітектура та ефективність
*   **Проблема (Воркери у фоні):** У файлі `update_worker.py` використовується глобальна змінна `_worker_running` та `_worker_task`. Цей патерн "синглтон" на рівні модуля не працює коректно, коли FastAPI запускається у багатопроцесорному середовищі (наприклад, з Gunicorn). Кожен процес матиме свого власного воркера, що призведе до конкурентних перегонів за базу даних і блокування.
*   **Як має бути:** Завдання, що працюють у фоновому режимі та звертаються до БД, мають використовувати зовнішні черги повідомлень (наприклад, Celery через Redis), або ж повинно бути реалізовано надійне блокування (locks) безпосередньо в Redis, яке перевіряє, який процес зараз обробляє чергу.
*   **Проблема (Обробка збоїв транзакцій БД):** У фонових завданнях і деяких викликах `crud` не використовується надійний `await db_session.rollback()` у блоках `except`, що може призвести до залипання транзакцій при використанні пулів з'єднань SQLAlchemy.
*   **Як має бути:** Транзакції завжди повинні мати структуру `try ... except ... finally` з явним rollback у разі помилки.

## 2. Модуль: `Nestworldvelocity/` (Velocity Proxy Плагін)

### Ефективність
*   **Проблема (Надмірний поллінг):** Плагін активно використовує механізм регулярного опитування API (polling) для перевірки статусу створення та запуску острова (`pollForRunningAndConnect`). Це створює значне та непотрібне навантаження на API та проксі-сервер, особливо при великій кількості одночасних підключень.
*   **Як має бути:** Замість поллінгу слід використовувати WebSocket підключення для очікування події від API. Плагін може відкрити одне спільне з'єднання (або використовувати Redis Pub/Sub, якщо Velocity підтримує це), щоб API миттєво повідомляло Velocity, коли острів стає доступним (Status: RUNNING).

### Архітектура та адміністрування
*   **Проблема (Архітектура та переадресація):** У `PlayerConnectionListener` є ризики витоку пам'яті: карти `pendingStartPlayers` та `pendingStopTasks` можуть накопичувати залишені записи, якщо процеси не завершуються очікувано або якщо гравець часто перепідключається.
*   **Як має бути:** Потрібно гарантувати видалення записів в `finally` або через тайм-аут-механізм очищення.
*   **Адміністрування:** Команди адміністрування (наприклад, `warp-admin`) не мають захисту паролем або API-ключем при зверненні до внутрішніх маршрутів API. Якщо бекенд не перевіряє джерело запиту, будь-хто з доступом до мережі бекенду зможе виконувати команди.

## 3. Модуль: `mods-server/` (Серверний мод Forge)

### Архітектура та ефективність
*   **Проблема (Блокуючі I/O операції):** У класі `NestworldModsServer.IslandProvider`, метод `getCachedTeamId` може блокувати основний потік сервера Minecraft (Server Thread), роблячи синхронний HTTP-запит до API (`refreshAndGetTeamId`), якщо кеш порожній. Це викликає лаги або навіть падіння сервера через "Tick too long".
*   **Як має бути:** Всі мережеві запити, звернення до файлової системи та інші тривалі операції мають виконуватися асинхронно за допомогою `CompletableFuture.supplyAsync()` або аналогів, а результати мають застосовуватися до основного потоку через `server.execute(...)`.
*   **Проблема (Жорсткий таєм-аут та відключення):** Планувальник "замороження" (`freezeTask`) скасовується лише якщо гравець заходить назад на сервер, але немає перевірки на те, чи запит замороження дійсно надіслано і оброблено. Крім того, WebSocket клієнт (`IslandWebSocketClient`) має логіку, яка просто виводить повідомлення при відключенні (`onClose`), але не має надійного механізму автоматичного перепідключення з експоненціальною затримкою.
*   **Як має бути:** WebSocket клієнт повинен мати автоматичний механізм reconnect. Запити на зміну стану (freeze/stop) повинні мати політику повторних спроб (retry policy) на випадок тимчасової недоступності API.

## 4. Модуль: `RealMarket/` (Мод економіки Forge)

### Ефективність
*   **Проблема (Синхронізація інвентарю):** Коли мод надсилає запит на синхронізацію інвентарю (`/inventory/sync`), він очікує і може робити блокуючі дії на стороні Forge, а API обчислює хеші великих списків товарів. Крім того, коли WebSocket надсилає повідомлення про купівлю на острів, процес видобутку предметів з AE2 (`executePurchaseAsync`) може бути відкладено через затримки I/O, що ускладнює роботу з AE2.
*   **Як має бути:** Операції з інвентарем та транзакції мають працювати за чергою з оптимізованими батчами (обробляти пачками), і ні в якому разі не блокувати головний потік.
*   **Безпека (Довіра до клієнта):** Клієнтська сторона (модифікація) не має остаточної перевірки "Azuriom ID" при відкритті UI для торгівлі, частково покладаючись на серверну верифікацію, що є правильним. Але якщо пакет `PacketTrade` не матиме жорсткої перевірки прав доступу чи лімітів на стороні API, можливі атаки "DDoS" або зловживання економікою.

## 5. Модуль: `FTB-Quests-1.20.1-main/`

### Архітектура
*   **Проблема (Приховування винятків):** У процесі розбору конфігурацій (наприклад, у класі `IntProperty.java` або інших класах `ThemeProperty`) винятки обгортаються у порожні блоки `try { ... } catch (Exception ignored) { }`. Це так зване "swallowing exceptions" (проковтування помилок). Якщо адміністратор налаштує невірний параметр квесту, помилка пройде мовчки і система просто застосує значення `null` або дефолтне.
*   **Як має бути:** Всі винятки потрібно логувати (`LOGGER.warn(...)`), щоб адміністратор сервера міг бачити в консолі, які саме властивості чи квести були налаштовані некоректно і чому їх не вдалося завантажити.

## Загальні рекомендації для адміністративного управління
*   Зараз система покладається на внутрішньоігрові команди або базові HTTP-ендпоінти без належного рівня аутентифікації. Для ефективного управління всією системою як адміністратор:
    1. Необхідно запровадити **API Key Auth** (для міжсерверної взаємодії між API, Velocity та модами) і **Admin Roles** (для гравців-адміністраторів або зовнішніх панелей).
    2. Розробити **Dashboard** або використати адмінські команди через RCON/Velocity з правами (`velocity.admin`), які б дозволяли бачити стан усіх інстансів (островів) та примусово змінювати їх статус (наприклад, знімати завислі острови).
