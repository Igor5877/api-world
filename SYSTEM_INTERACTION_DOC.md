# Взаємодія компонентів системи SkyBlock

Цей документ описує, як чотири компоненти (Velocity, API, Forge Mod та FTB Quests) спілкуються між собою для створення цілісного ігрового досвіду.

## 1. Повний цикл входу гравця

1.  **Вхід у Proxy (Velocity):**
    *   Гравець підключається до Velocity.
    *   Плагін `Nestworldvelocity` перехоплює підключення і відправляє гравця на "Хаб" (тимчасовий сервер).
2.  **Запит до API:**
    *   Velocity робить асинхронний HTTP-запит до **API** (`GET /api/v1/islands/{uuid}`).
    *   **API** перевіряє стан острова в базі даних та у LXD.
3.  **Запуск/Створення острова:**
    *   Якщо острова немає — **API** запускає фоновий процес клонування контейнера.
    *   Якщо острів зупинений — **API** запускає контейнер у LXD.
    *   Velocity отримує відповідь, що острів запускається (`PENDING_START`).
4.  **Завантаження Minecraft (Forge Mod):**
    *   Контейнер запускається. Minecraft Forge завантажується.
    *   **Forge Mod** читає файл `skyblock_island_data.toml` і дізнається свій контекст.
    *   **Forge Mod** надсилає сигнал в **API** (`POST /islands/{owner_uuid}/ready`).
5.  **Готовність (API):**
    *   **API** встановлює прапор `minecraft_ready = true` у базі даних.
    *   **API** розсилає WebSocket-повідомлення про готовність.
6.  **Перенаправлення (Velocity):**
    *   Плагін Velocity (через опитування або WebSocket) отримує сигнал готовності.
    *   Velocity дізнається внутрішню IP-адресу контейнера від API.
    *   Velocity реєструє новий сервер у себе в пам'яті та миттєво переключає гравця з Хаба на його острів.

---

## 2. Командна робота та квести під час гри

*   **Зміна команди:** Гравці використовують команди у Velocity (наприклад, `/team accept`). Velocity передає ці запити в API.
*   **Синхронізація (WebSocket):**
    *   Як тільки API оновлює склад команди в БД, воно відправляє сигнал через WebSocket на **Forge Mod** відповідного острова.
    *   **Forge Mod** миттєво оновлює `IslandData` та `TeamManager` у **FTB Quests**.
*   **Виконання квестів:** Коли гравець виконує дію, **FTB Quests** звертається до **Forge Mod** через `QuestTeamBridge`, щоб перевірити: "Чи справді цей гравець є членом команди цього острова?" та "Чи знаходиться він на правильному сервері?".

---

## 3. Ресурс-менеджмент (Auto-Freeze / Stop)

1.  **Вихід гравця:** Останній гравець виходить з острова.
2.  **Таймер (Forge Mod):** Мод запускає 5-хвилинний таймер.
3.  **Запит на заморозку:** Після таймера мод надсилає запит в **API** (`POST /islands/{uuid}/freeze`).
4.  **Заморозка (API):** API через LXD заморожує процеси сервера. Стан сервера (RAM) зберігається, але CPU не споживається.
5.  **Stop (Velocity):** Якщо гравець виходить з мережі зовсім, Velocity також може ініціювати зупинку контейнера через певний час.

---

## 4. Методи зв'язку (Технічно)

| Звідки -> Куди | Тип зв'язку | Що передається |
| :--- | :--- | :--- |
| **Velocity -> API** | REST HTTP (JSON) | Запити на старт, статус острова, керування командами. |
| **Forge Mod -> API** | REST HTTP (JSON) | Сигнал готовності (`ready`), запит на заморозку (`freeze`), запит даних команди. |
| **API -> Forge Mod** | **WebSocket** | Оновлення складу команди в реальному часі (`TEAM_UPDATED`). |
| **API -> Velocity** | **WebSocket** | Сповіщення про готовність острова до підключення. |
| **Forge Mod -> FTB Quests** | Java API (Direct call) | Синхронізація членів команди, блокування прогресу. |
| **API -> LXD** | Unix Socket / HTTP | Керування контейнерами (clone, start, stop, freeze). |

### 5. Особливості розгортання в Production (SSL/Nginx)

При використанні реального домену (наприклад, `nestworld.site`) з підтримкою HTTPS, з'являються додаткові вимоги до конфігурації.

#### Формат WebSocket адрес
Для підключення використовуйте: **`wss://nestworld.site/ws/<PLAYER_UUID>`**

**Чому це важливо:**
1.  **Протокол WSS**: Якщо сайт працює на HTTPS, браузери та клієнти забороняють підключення через незахищений `ws://`. Це призводить до помилки **301 (Redirect)** або блокування з'єднання.
2.  **Без префікса `/api/v1`**: WebSocket ендпоінт зареєстрований як `/ws/`, а не `/api/v1/ws/`.
3.  **Redis**: Для роботи WebSocket-менеджера **Redis повинен бути запущений**. Він координує повідомлення між різними воркерами API.

#### Налаштування Nginx (Reverse Proxy)
Щоб WebSocket працював через Nginx, конфігурація `location` повинна виглядати приблизно так:

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:8000;  # Порт вашого FastAPI
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /api/ {
    proxy_pass http://127.0.0.1:8000;
    # Стандартні налаштування для REST API
}
```

#### Діагностика з'єднання
Якщо ви отримуєте помилки (301, 404), проведіть наступну перевірку:

1.  **Перевірка роботи API**:
    `curl http://nestworld.site:8000/`
    Має повернути: `{"message": "Welcome to the SkyBlock LXD Manager API"}`

2.  **Перевірка наявності маршруту WebSocket**:
    `curl -I http://nestworld.site:8000/ws/test-uuid`
    *   **405 або 426**: Маршрут знайдено (це добре).
    *   **404**: Маршрут не знайдено. Перевірте, чи API запущено без параметра `--root-path`.

3.  **Тест через wscat (Production)**:
    `wscat -c wss://nestworld.site/ws/02034378-1e7b-311c-b350-17090a13dab1`

#### Фінальний чек-лист підключення
1.  **301 Redirect**: Якщо отримуєте 301 — змініть `ws://` на `wss://`.
2.  **404 Not Found**: Якщо отримуєте 404 — перевірте, чи не додає ваш клієнт префікс `/api/v1/`. WebSocket повинен йти за шляхом `/ws/` від кореня.
3.  **Forge Mod Fix**: Якщо мод не може підключитися, переконайтеся, що в коді `SkyBlockMod.java` видаляється префікс `/api/v1` при формуванні `wsUrl`.
